## 3. 주요 기술 결정

### 3-1. 회의 제목 변경 결함 원인 진단 (핸드오프 §4.8 요청)

**증상**: 재편집 모드에서 회의 제목을 변경해도 반영 안 됨.

**진단**:
- `Editing.tsx:52`에 `apiBase = editMode === 'meeting' ? '/meetings' : '/sessions'`로 PATCH endpoint를 분기
- 블록 PATCH 4건(`importance`, `text`, `split`, `merge`)은 모두 `${apiBase}/...`로 분기 처리되어 정상 동작
- **`saveMetadata`(line 378-383)만 분기 누락** — 항상 `updateMetadata(...)` → `PATCH /sessions/{id}/metadata` 호출
- 재편집 모드에서는 `session.session_id`가 `mtg_xxx`로 시작 → sessions 라우터에서 못 찾고 404 (또는 무동작 → 사용자 입장에서 "미반영")

**fix**: `saveMetadata`에 `editMode === 'meeting'` 분기 추가, meeting 모드는 `api.patch('/meetings/{id}', { metadata: { [field]: value } })` 호출. backend `history.py:127-147`의 PATCH 엔드포인트는 이미 `metadata.title`을 화이트리스트에 포함하므로 backend는 변경 없음.

**향후 유사 패턴 방지**: 새 metadata PATCH 함수를 만들 때 `apiBase` 분기 의식. 또는 `updateMetadata`/`updateMeeting` 어느 쪽을 호출할지 결정하는 헬퍼를 별도 만드는 게 안전 — 본 fix는 최소 범위 변경에 그침.

### 3-2. user 태그 필터링 위치 — Phase 1A와 동일 패턴 유지

기획 §4.2 권고대로 `summary_assembler.extract_action_items`의 정규식만 변경. assignee 값은 여전히 이름만 저장(`님` 제외), `ActionItem` 모델 무변경. 호출처 변경 0.

### 3-3. F/U 정렬 알고리즘 — 출현 순서 보존 안정 정렬

기획 §2-1 "같은 인물의 task가 인접하도록 정렬" 구현: assignee가 처음 등장한 인덱스를 키로 사용한 안정 정렬. 회의 진행 순서대로 인물이 등장하는 자연 흐름을 보존하면서 같은 인물 task만 묶임. None assignee는 `￿` 키로 끝으로 보냄.

### 3-4. _build_slack_message → 호환 alias 유지

기존 함수명을 외부에서 import할 수 있어 `_build_slack_message = _build_main_message` alias 유지. 향후 정리 시 grep으로 확인 후 제거 가능.

### 3-5. legacy `@assignee` 정규식 fallback 유지

기획 §6 "기존 회의록은 그대로 둠"이지만 사용자가 구 회의록을 "재요약" 호출 시 정규식이 못 잡으면 assignee=None으로 손실. legacy fallback을 두면 재요약 결과가 자동으로 신규 구조로 정상화됨(claude 응답이 신규 [xxx님] 형식이라). 안전망 성격.

### 3-6. delete 흐름의 ts 식별 — 신구조 우선 + legacy fallback

기존 `delete_slack_message`는 `slack_sent.message_ts == req.message_ts` 비교. 신규 구조에서는 main_ts가 `messages.main.ts`에 들어가서 `message_ts`(legacy 필드)는 None일 수 있음. → 분기: `messages.main.ts` 또는 `message_ts` 어느 쪽이든 매칭되면 삭제 처리. 신규 송신은 backend가 둘 다 채워주므로 양쪽 패턴 모두 동작.
